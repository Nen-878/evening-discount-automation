# Архитектура решения

## Пользовательский контур

```text
Start_App.vbs
    ↓
pythonw / pyw
    ↓
app.pyw → app.py (tkinter GUI)
    ↓
run_pipeline(...)
    ↓
output: рабочий Excel + печатный лист
```

GUI не содержит бизнес-правил. Он только выбирает входной файл, запускает pipeline, показывает KPI и переводит технические ошибки в понятные пользователю сообщения.

## Pipeline

```text
input_1c.xlsx
    ↓
loader.py
    ↓
validation.py
    ↓
decision_engine.py + rules.py
    ↓
pricing.py
    ↓
kpi.py
    ↓
excel_report.py ─────→ итоговый отчет
    ↓
print_sheet.py ──────→ печатные карточки READY
```

## Разделение решений

### BUSINESS_STATUS
Отвечает на вопрос: **что разрешено бизнесом и регламентом?**

### EXECUTION_STATUS
Отвечает на вопрос: **можно ли технически выполнить это решение сегодня?**

Это предотвращает ситуацию, когда ошибка штрихкода скрывает более важное решение, например окончание срока годности или нарушение маржинальности.

## Границы безопасности

- нет восстановления потерянных цифр из scientific notation;
- нет автоматического выбора одного штрихкода из нескольких;
- нет EAN checksum как выдуманного бизнес-инварианта;
- нет автоматического обхода Margin Guardrail;
- нет генерации нового сканируемого barcode без кассовой спецификации;
- каждая строка входа получает объяснимое решение и не исчезает из отчета.

## Почему локальное приложение

Для тестового выбран файловый контур: 1С выгружает Excel, локальное приложение применяет правила и формирует рабочий результат. Источник данных отделен от decision engine, поэтому в production Excel можно заменить прямой интеграцией с 1С/API без переписывания бизнес-логики.
