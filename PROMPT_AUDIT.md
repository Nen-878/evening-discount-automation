# PROMPT_AUDIT.md

## 1. Pipeline & процесс

Решение построено как детерминированный pipeline: **сырая выгрузка 1С → валидация → бизнес-правила → решение → расчет цены → KPI → итоговый Excel → печатный рабочий лист**.

AI применялся как инженерный помощник, а не как runtime-компонент. Cursor использовался для первичной реализации модулей, тестов и Excel-отчета. ChatGPT использовался для формализации регламента, независимого review бизнес-логики, поиска краевых случаев, проверки экономических расчетов и пользовательского QA. В production-исполнении AI не принимает решения по товарам: все правила закодированы явно и воспроизводимо.

Архитектура разделяет:
- `BUSINESS_STATUS` — что разрешено/запрещено бизнесом;
- `EXECUTION_STATUS` — можно ли технически выполнить решение сегодня.

Это позволяет не смешивать бизнес-риск с качеством мастер-данных.

## 2. Критическое использование AI: что пришлось исправить

AI-результат не принимался «как есть». Реальная разработка прошла несколько циклов **генерация → независимая проверка → ручной пользовательский тест → исправление**.

### Бизнес-логика

1. **Data Quality перекрывал бизнес-решение.** В первой версии `DATA_QUALITY_REVIEW` по штрихкоду стоял выше проверки срока годности и маржи. Из-за этого товар, который уже нельзя продавать после 20:00, мог выглядеть просто как «проблема штрихкода». Исправление: сначала определяется `BUSINESS_STATUS`, затем отдельно `EXECUTION_STATUS`.
2. **Scientific notation нельзя восстанавливать.** Значения вида `4.60701E+12` не преобразуются в «предполагаемый полный EAN»: исходная точность потеряна.
3. **Несколько штрихкодов нельзя молча сводить к одному.** Значения через `;` отправляются на исправление мастер-данных.
4. **EAN-13 checksum не является бизнес-требованием.** Первичная идея такой проверки была отвергнута: внутренние идентификаторы могут не быть EAN-13, а регламент этого не требует.
5. **Пробелы по краям — не причина терять выручку.** `strip()` признан безопасной технической нормализацией; исходное значение сохраняется для аудита.
6. **Слепое −30% нарушает Margin Guardrail.** Высокозатратные позиции получают `MARGIN_ALERT` и не идут в автоматическое исполнение.
7. **Округление «до 5 или 10 ₸» неоднозначно.** Допущение зафиксировано явно: округление вниз до 5 ₸ в пользу покупателя.

### UX и эксплуатация

8. **Денежный формат оказался зависимым от локали Excel.** На одном Windows-компьютере ячейки с тенговым заголовком визуально показывались как рубли. Исправление: валютный символ убран из числового формата ячеек и оставлен в заголовках/тексте, чтобы результат не зависел от системной валюты.
9. **Закрепление областей было слишком агрессивным.** На листах директора и контроля данных верх занимал большую часть экрана. Исправление: закрепление оставлено только там, где оно реально помогает — в длинных рабочих таблицах.
10. **Кириллица в именах файлов внутри ZIP ломалась на конкретном Windows-архиваторе.** Финальный Windows-пакет использует ASCII-имена файлов; русские названия создаются уже локально приложением.
11. **CMD оказался плохим интерфейсом для магазина.** Пользовательский запуск переведен на GUI через `pythonw/pyw`, без видимой консоли. Технический `run.py` сохранен для разработчика/CI.
12. **Технические статусы были непонятны обычному сотруднику.** Рабочие листы переведены с `BLOCK_*`/`DATA_QUALITY_REVIEW` на язык действий: «Нужно решение директора», «Исправить данные», «Не уценять», «Клеить стикер».
13. **Технические traceback заменены пользовательскими сообщениями.** Например, если итоговый Excel открыт, сотрудник видит просьбу закрыть файл, а не `PermissionError`.

### Печатный контур — осознанное ограничение

Добавлен печатный рабочий лист по позициям `AUTO_DISCOUNT + READY`: товар, номер штрихкода из 1С, старая и новая цена, остаток и срок продажи.

При этом **новый графический barcode намеренно не генерируется**. В исходных материалах нет спецификации символогии (EAN/Code128 и т. п.), размера этикетки, модели принтера, кассового PLU и количества контейнеров/фасовок. Генерировать сканируемый код или количество физических наклеек без этих данных было бы AI-додумыванием кассового процесса. Поэтому одна печатная карточка соответствует одной готовой товарной позиции, а число физических стикеров определяет сотрудник по фактической фасовке.

## 3. Экономический эффект

На фактической выгрузке из 107 строк:

Бизнес-решения:
- `AUTO_DISCOUNT` — 50;
- `BLOCK_CATEGORY` — 31;
- `BLOCK_EXPIRY` — 19;
- `BLOCK_BRAK` — 1;
- `MARGIN_ALERT` — 6.

Из 50 бизнес-кандидатов 43 технически готовы к исполнению (`READY`), 7 требуют исправления мастер-данных.

Экономика:
- теоретический промо-потенциал всех 50 `AUTO_DISCOUNT`: **437 127,5 ₸**;
- реально исполнимая сегодня промо-выручка по 43 `READY`: **376 221 ₸**;
- промо-выручка под риском из-за качества мастер-данных: **60 906,5 ₸**;
- себестоимость 43 готовых позиций: **286 686 ₸**;
- выручка сверх себестоимости по готовому плану: **89 535 ₸**.

Теоретический потенциал и исполнимая сегодня выручка намеренно разделены, чтобы не завышать эффект.

## 4. Рекомендации дирекции

1. Хранить штрихкод в 1С как строковое поле и исключить scientific notation при экспорте в Excel.
2. Не хранить несколько штрихкодов в одной ячейке; при необходимости использовать отдельный справочник связей.
3. Добавить в выгрузку поля `Годен_до`, `Количество_упаковок/контейнеров` и технический признак готовности карточки к кассовой акции. Последнее позволит в будущем генерировать точное количество этикеток и безопасно интегрировать специализированный принтер.

## UX-слой

Поверх детерминированного pipeline добавлен локальный GUI на стандартном `tkinter`. Он позволяет сотруднику выбрать выгрузку, запустить расчет без CMD, увидеть ключевые KPI, открыть итоговый Excel и отдельный печатный лист. AI/API при работе программы не используются.
